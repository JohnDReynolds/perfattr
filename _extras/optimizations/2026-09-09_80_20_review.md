# Simple 80/20 Performance Review

**Status:** Investigation complete September 9, 2026. All three recommendations were
implemented and verified the same day.

## Conclusion

Three contained changes appear worthwhile. The first is a substantial general win
for effective-dated preparation; the second is a small shared cleanup with broad
benefit; and the third materially improves selection from a large multi-portfolio
frame.

1. Vectorize the valid path for effective-dated classification assignment.
   **Implemented and verified.**
2. Replace the per-value Python identity type scan with pandas' public inferred-dtype
   check while retaining the existing trim and validation behavior. **Implemented and
   verified.**
3. Validate all portfolio codes but copy only the selected portfolio rows.
   **Implemented and verified.**

The other profiled calculations are already fast at the established input sizes.
Their remaining time is primarily required normalization, grouping, and production
reconciliation. No evidence supports removing checks, adding a dependency, or
undertaking a complicated refactor.

## Review constraints

This review sought simple changes with material end-to-end effects. It did not:

- change financial formulas, schemas, tolerances, warnings, or release gates;
- bypass caller-input validation or production reconciliation;
- mutate caller-owned DataFrames;
- add a runtime dependency;
- treat isolated microbenchmark speed as sufficient evidence; or
- modify production source code.

Temporary monkeypatch prototypes were used to test the leading ideas. They are not
part of the repository. All three recommendations subsequently received normal
implementation, focused tests, static analysis, and benchmark verification.

## Environment and method

Measurements used the project's Python 3.11.9 environment on Apple arm64 with pandas
3.0.5 and NumPy 2.4.6. Public operations received deterministic inputs constructed
before measurement. Each operation was warmed before timing.

The main profile used the established `monthly_121260` workload: 121,260 portfolio
rows, 121,260 benchmark rows, and 120 monthly periods. Candidate comparisons used
medians and, where practical, alternated baseline and candidate calls to reduce
temporal bias. `cProfile` identified call paths; its instrumented absolute times were
not compared with uninstrumented wall times.

Seven recorded samples produced these medians on the largest-row established

## Recommendation 1: vectorize effective-dated assignment

### Former cost

`_effective_mapped_identifiers` in `src/perfattr/mapping.py` converted every source
row to Python objects and called `_resolve_effective_identifier` separately. The
largest profile made 242,520 resolver calls across the two sides. The effective
assignment path accounted for about two thirds of the complete preparation call.

### Implemented shape

Use a sorted pandas `merge_asof`, grouped by source identifier, to find the latest
assignment beginning on or before each source period. Check vectorially that its
inclusive end contains the source-period end. Identifiers absent from the mapping
retain their existing identity fallback.

Keep the existing scalar resolver for invalid rows only. Calling it for the first
invalid source row preserves the precise distinction and error message for a gap
versus a classification boundary crossing. Financial roll-up remains unchanged.

### Prototype results

Alternating baseline and candidate calls produced:

| Workload | Baseline | Candidate | Time reduction | Speedup |
|---|---:|---:|---:|---:|
| `normal` | `0.127593 s` | `0.098957 s` | 22.4% | 1.289x |
| `selected_10x` | `0.462080 s` | `0.184158 s` | 60.1% | 2.509x |
| `monthly_121260` | `0.846406 s` | `0.284001 s` | 66.4% | 2.980x |
| `history_25y` | `0.410935 s` | `0.274171 s` | 33.3% | 1.499x |

Representative returned frames were exactly equal. With the temporary vectorized
candidate installed, all 618 project tests passed.

Incremental Python-traced allocation changed as follows:

| Workload | Baseline | Candidate | Change |
|---|---:|---:|---:|
| `normal` | 3.0 MiB | 2.0 MiB | -1.0 MiB |
| `selected_10x` | 15.4 MiB | 17.5 MiB | +2.1 MiB |
| `monthly_121260` | 30.6 MiB | 34.0 MiB | +3.4 MiB |
| `history_25y` | 9.6 MiB | 9.0 MiB | -0.7 MiB |

The largest traced increase is modest relative to the approximately threefold elapsed
speedup. This is the clearest 80/20 opportunity in the project.

### Completed implementation checks

- Deterministic source-row and result ordering is preserved.
- Inclusive boundary semantics are preserved.
- Identity fallback for identifiers wholly absent from the mapping is preserved,
  including for an empty effective-dated mapping.
- Exact gap, boundary-crossing, overlap, and ambiguity failures are preserved.
- A seeded differential check matched 100 randomized valid histories and exact error
  text for 100 randomized invalid histories against the former scalar path.
- The complete gate passed with 620 tests, Pylint 10.00/10, zero Pyright errors or
  warnings, and the seven-sample direct preparation benchmark.

## Recommendation 2: remove the redundant Python identity scan

### Former cost

`normalize_identity` in `src/perfattr/_validation.py` first executes
`Series.map(lambda value: isinstance(value, str))` and then performs the required
string conversion and trimming pass. The first operation is a Python callback for
every value. On the largest arithmetic profile, identifier normalization consumed
about one third of the instrumented public call.

### Implemented shape

Use the public `pandas.api.types.infer_dtype` result to reject non-string columns,
with an explicit empty-Series case, then retain the existing `string[python]`
conversion, whitespace trimming, blank rejection, and leading-zero behavior. This
removes only the redundant Python callback scan.

Pandas reports a categorical Series by its container dtype rather than its observed
value types. A narrow fallback therefore infers the categorical's observed values.
This preserves the former acceptance of an all-string categorical, including one
whose definition contains an unused non-string category.

### Prototype results

Fifteen-sample medians on the largest-row workload were:

| Public operation | Baseline | Candidate | Time reduction |
|---|---:|---:|---:|
| Arithmetic attribution | `0.203776 s` | `0.189841 s` | 6.8% |
| Geometric attribution | `0.167586 s` | `0.155570 s` | 7.2% |
| Currency attribution | `0.169021 s` | `0.153405 s` | 9.2% |
| Static preparation | `0.256732 s` | `0.242045 s` | 5.7% |

At prototype time, effective preparation was dominated by its scalar dated-assignment
loop, so the standalone identity change was lost in ordinary variation there.

All representative results remained exactly equal, and all 618 tests passed with the
temporary candidate. This is not a large optimization by itself, but it is a small,
shared, low-complexity improvement affecting most public DataFrame boundaries.

### Verified production results

Seven paired rounds alternated the former element-wise implementation and the
production inferred-dtype implementation on the established `monthly_121260`
workload. Phase 1 was active for both effective-preparation variants. Every public
result frame was exactly equal.

| Public operation | Former element scan | Production inference | Time reduction |
|---|---:|---:|---:|
| Arithmetic attribution | `0.204727 s` | `0.188145 s` | 8.1% |
| Geometric attribution | `0.168559 s` | `0.153062 s` | 9.2% |
| Currency attribution | `0.166170 s` | `0.150433 s` | 9.5% |
| Static preparation | `0.255448 s` | `0.236632 s` | 7.4% |
| Effective preparation | `0.276513 s` | `0.262365 s` | 5.1% |

At one-decimal MiB precision, peak Python-traced allocation was unchanged for all
five operations except arithmetic attribution, which declined by 0.1 MiB. The
official seven-sample large-workload benchmarks also completed successfully:

- arithmetic attribution: `0.1874 s`, 89.1 MiB peak traced allocation;
- static preparation: `0.2378 s`, 30.5 MiB;
- effective preparation: `0.2607 s`, 33.3 MiB; and
- currency attribution: `0.1474 s`, 64.2 MiB.

### Completed implementation checks

- Seventeen focused tests cover object and nullable strings, NumPy strings, string
  categoricals, unused mixed categorical categories, empty columns of several dtypes,
  nulls, mixed numerics, bytes, booleans, datetimes, blanks, trimming, leading zeroes,
  and caller-frame ownership.
- All affected public-boundary tests passed without changing their expectations.
- The complete gate passed with 637 tests, Pylint 10.00/10, zero Pyright errors or
  warnings, and direct core, preparation, geometric, and currency measurements.
- No validation behavior, public schema, tolerance, dependency, or threshold changed.

## Recommendation 3: copy only selected portfolio rows

### Former cost

`select_portfolio` in `src/perfattr/preparation.py` deep-copied the entire input frame,
normalized its `portfolio_code` column, filtered the requested code, and then
deep-copied the selected rows again. Validation of every code is required, but a copy
of every nonselected financial and metadata column is not.

### Implemented shape

Normalize and validate the complete `portfolio_code` Series without modifying the
caller. Build the selection mask from that normalized Series, copy only matching
rows, and assign their normalized codes to the returned frame.

### Prototype results

The test frame contained 606,300 rows, ten columns, and 100 portfolios. Its deep size
was 244.6 MiB, and the requested portfolio contained 1% of the rows.

| Variant | Median | Time reduction | Speedup | Peak traced allocation |
|---|---:|---:|---:|---:|
| Current | `0.140989 s` | — | — | 89.1 MiB |
| Copy only selected rows | `0.124699 s` | 11.6% | 1.131x | not isolated |
| Selected-row copy plus recommendation 2 | `0.084053 s` | 40.4% | 1.677x | 42.2 MiB |

The combined candidate produced an exactly equal result and passed all 618 tests.
The impact naturally depends on frame width and the selected fraction; it is most
valuable for a large master file containing many portfolios.

### Verified production results

Seven paired rounds alternated the former whole-frame-copy implementation and the
production selected-row-copy implementation. Phase 2 identity inference was active
for both variants, isolating the Phase 3 change. The master frame contained 606,300
rows, ten columns, and 245.2 MiB of deep input data. Each returned frame was exactly
equal.

| Selected rows | Former time | Production time | Time reduction | Peak allocation |
|---:|---:|---:|---:|---:|
| 1% | `0.104922 s` | `0.087261 s` | 16.8% | 89.1 → 42.8 MiB |
| 10% | `0.104892 s` | `0.088824 s` | 15.3% | 89.1 → 49.1 MiB |
| 50% | `0.118456 s` | `0.102902 s` | 13.1% | 124.1 → 97.5 MiB |
| 100% | `0.116105 s` | `0.100608 s` | 13.3% | 124.3 → 111.6 MiB |

The optimization therefore reduces both elapsed time and peak allocation at every
measured fraction. Its primary benefit remains the common case in which a relatively
small portfolio is selected from a much larger master frame.

### Completed implementation checks

- The complete `portfolio_code` Series is normalized and validated before filtering,
  so an invalid nonselected row still raises the same error.
- Selection remains exact, case-sensitive, stable, independently owned, and
  zero-indexed, with the normalized code retained for lineage.
- A focused implementation guard rejects any return to deep-copying all input rows.
- The complete gate passed with 641 tests, Pylint 10.00/10, and zero Pyright errors or
  warnings.
- No validation behavior, output schema, dependency, or threshold changed.

## Lower-priority finding: reuse strict CSV scan results

Loading a valid 9.4 MiB, 121,260-row performance CSV took a median `0.2774 s`. The
reader intentionally performs a strict Python CSV scan before pandas parsing to
enforce quoting and uniform row width. After parsing, it scans every field again to
remove wholly blank records.

A prototype retained blank physical-line numbers during the mandatory strict scan and
passed them to `pandas.read_csv`, avoiding the second blank-record scan. The result was
exactly equal and improved from `0.276986 s` to `0.226602 s`, an 18.2% reduction and
1.222x speedup.

This is safe in principle, but it saves only about 0.05 seconds at the measured size
and requires coordinated changes to two private reader functions plus blank-line
tests. Defer it until loading is observed as a real bottleneck. A separate prototype
that built the DataFrame directly from the Python CSV records was 17.9% slower than
the baseline and should not be pursued.

The strict first pass should not simply be removed: doing so would weaken established
CSV validation to obtain a benchmark win.

## Investigated but not recommended

### Hierarchy identifier-set construction

Constructing a leaf-identifier set by iterating 121,260 values took `0.016739 s`;
using the already validated column's unique values took `0.002265 s`. Although the
isolated operation was 7.39x faster, the maximum end-to-end saving is only about 4%
of the `0.3476 s` hierarchy call. This is a micro-optimization, not an 80/20 win.

The hierarchy's larger costs are required additive grouping, source-result
validation, and independent parent/root reconciliation. Removing their sorts or
checks would risk deterministic arithmetic or weaken production evidence.

### Arithmetic, geometric, and currency calculations

Apart from shared identity validation, no single simple hotspot dominates these
calculators. Each already processes roughly a quarter-million side rows in about
`0.16` to `0.21` seconds while returning full result and reconciliation frames.
Restructuring the pandas groupings or merging the public preparation and calculation
contracts would be a larger architectural change with little absolute benefit.

### Multi-period currency roll-up

The largest established case completes in about `0.05` seconds. Optimization is not
warranted.
